# Brian

A minimal local chatbot that talks to the Anthropic Claude API through a small FastAPI backend. Its purpose is to prove an API key works end to end.

- Backend: `app.py` (FastAPI + official `anthropic` SDK, streams replies as Server-Sent Events)
- Frontend: `static/index.html` (plain HTML/CSS/JS, served by FastAPI)
- Chats are stored in your browser's localStorage under `brian.chats`

## 1. Setup (once)

Requires Python 3.11 or newer.

macOS / Linux:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Windows PowerShell:

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## 2. Set your API key for this terminal session

Create a key at https://console.anthropic.com → **Settings → API Keys**. Never put the key in a file in this folder; set it only in your terminal session.

macOS / Linux:

```bash
export ANTHROPIC_API_KEY="your-key-here"
```

Windows PowerShell:

```powershell
$env:ANTHROPIC_API_KEY = "your-key-here"
```

The variable only lives as long as that terminal window. Open a new terminal and you need to set it again.

## 3. Run

```bash
uvicorn app:app --host 127.0.0.1 --port 8000
```

Open http://127.0.0.1:8000 and say "Hello".

If the key is missing, the server still starts, logs an error, and the chat shows a clear message. A wrong key shows a "key was rejected (401)" message.

## 4. Change the model

The default model is `claude-sonnet-5-5`. Set `BRIAN_MODEL` before starting the server to use a different one:

```bash
export BRIAN_MODEL="claude-opus-5-5"
```

```powershell
$env:BRIAN_MODEL = "claude-opus-5-5"
```

Brian sends `output_config.effort = "low"` to keep chat replies quick. That works on current Claude models (Sonnet 5.5, Opus 5.5, Haiku 5.5 and others). Very old models that don't support effort will return an error; remove that line in `app.py` if you need one of them.

## 5. Login (optional locally, required when hosted)

Login turns on when both of these are set. Locally you can leave them unset.

| Variable | Meaning |
|---|---|
| `BRIAN_LOGIN_EMAIL` | The email to log in with |
| `BRIAN_LOGIN_PASSWORD` | The password (use a long one on a public site) |
| `BRIAN_SESSION_SECRET` | Random string that signs the login cookie. If unset, a random one is made at startup and everyone is logged out on restart |

After 5 wrong attempts from one address, login is blocked for 15 minutes.

## 6. Hosting on Render

`render.yaml` describes the service. In the Render dashboard choose **New → Blueprint**, connect this GitHub repo, and enter `ANTHROPIC_API_KEY`, `BRIAN_LOGIN_EMAIL` and `BRIAN_LOGIN_PASSWORD` when asked. On Render, Brian stays locked (503) until the login variables are set.

The free plan sleeps after about 15 minutes without traffic; the first visit after that takes up to a minute.

## 7. GitHub Pages version (`docs/`)

`docs/index.html` is a static build of Brian for GitHub Pages. It has no backend: the browser calls the Anthropic API directly with the key you enter at login. The key is kept only in that browser (session only, or on the device if you tick "Remember").

- The email/password check runs in the browser against a SHA-256 hash in the page. It only gates the page; anyone can read the code. The API key is the real lock.
- Your Anthropic organisation must allow browser (CORS) requests. Some organisations turn this off; the login then says so, and you need the server version above.
- The model and settings are constants at the top of the script in `docs/index.html`.

## 8. Brian case-knowledge system (Claude Artifact + Claude Code skill)

Brian captures the context of closed cases and makes it reusable. One artifact, the **Brian library**, has two modes, toggled at the top of its sidebar:

- **Ask**: for any case team that wants context. One large question field at the top and, below it, case cards for every case on file, filtered by functional area (Procurement, Pricing, ...) and by practice area (the client's industry). Brian gives an overview of all cases, the past cases most relevant to a new one (matched on functional area first), one case in depth, or lessons across cases. Brian reads case contexts and opens file digests when a context isn't enough. Guided by the context and digests, it can also open the **original files in the case SharePoint** (specific slides, worksheets or pages) through the asking person's Microsoft 365 connector, with their own SharePoint permissions. It cites its sources.
- **Get asked**: a case team member enters the case code and chooses how to be debriefed: **step by step**, or **all questions at once** (the full list in one message, answered in one go, for example by dictating; follow-ups come back as one list). In all-at-once mode Enter adds a line and Ctrl+Enter sends, so dictation can't send half an answer. The interview is the knowledge-capture team's procurement-project-debrief skill (`docs/team/`), adapted: time first, four linked blocks (project context, outcomes, procurement know-how, key documents), a "# Project knowledge record" at the close. "Finish & update case context" merges it into the case's living context and refreshes its card.

The design memo is [docs/MEMO.md](docs/MEMO.md). Everything else lives in `.claude/skills/brian/`:

| File | Purpose |
|---|---|
| `SKILL.md` | The `brian` skill for Claude Code: overview, SharePoint folder layout, library database layout, rules |
| `review.md` | `/brian review <case code>`: read the case file tree; write `Brian/open_questions.txt`, a first case card and file digests; load them into the library |
| `sync.md` | `/brian sync <case code>`: merge unmerged debriefs, refresh the card, copy transcripts to `Brian/raw_transcripts/` and uploads to `Brian/files/`, write `Brian/context.md` |
| `formats.md` | Formats of the questions file, transcripts, context.md, case card, file digests and `brian.json` |
| `template/brian.html` | The library page (both modes) |
| `template/interview_prompt.txt` | The debrief, adapted from the team's skill; gets the case's open questions, current context and the elapsed time |
| `template/context_prompt.txt` | How a debrief is merged into `context.md` |
| `template/card_prompt.txt` | How the case card is extracted from `context.md` |
| `template/ask_prompt.txt` | Brian Ask |
| `scripts/write_transcript.py` | Writes a raw transcript from a stored interview (used by sync) |
| `examples/open_questions_MOCK.txt` | Mock questions for the fictional demo case `DEMO-LIGHTHOUSE` |

### How it fits together

1. Sync the case's SharePoint library with OneDrive and start Claude Code in that folder. Run `/brian review <CODE>`. It writes `Brian/open_questions.txt` and loads the questions, a first case card and file digests into the library. The case appears in Brian Ask.
2. Case team members open the library, switch to "Get asked", enter the case code and run one or more debriefs. They can attach PDFs, images and text files.
3. "Finish & update case context" merges the debrief into the case's living `context.md` and updates its card.
4. `/brian sync <CODE>` merges any debrief nobody finished, and copies transcripts, uploads and `context.md` into `Brian/` in the SharePoint.
5. A new case team asks Brian Ask which past cases help, and drills into the relevant ones.

### The artifact

- No backend and no API key: replies come from the Artifact `sample` capability on the viewer's own Claude account. Prompts go in as a leading user turn, because Artifacts have no page-controlled system prompt. Model: `claude-sonnet-5-5`, falling back to the platform default. Brian Ask uses page tools (`get_case_context`, `list_case_files`, `read_case_file`) where the viewer's app supports them, and otherwise picks the relevant cases first and puts their contexts in the prompt.
- Capabilities: `sample` (with images), `db` and `user` (case data), `assets` (uploads; Contributors may upload), `downloads` (transcript .txt), `mcp` (the viewer's Microsoft 365 connector, `read_resource` only, for original SharePoint files; each viewer allows it once).
- Database: `cases/<CODE>` (questions, card, context), `cases/<CODE>/docs/<id>` (file digests), `cases/<CODE>/chats/<id>` (debriefs), `cases/<CODE>/files/<assetId>` (uploads). Everyone the library is shared with sees every case in it; client names may show.
- Uploads accept PDF, PNG, JPEG, GIF, WebP, .txt, .md, .csv and .json up to 20 MB. Word, Excel, PowerPoint and Outlook files aren't accepted by the artifact's file store. Brian reads text files up to 30,000 characters and images; PDFs are stored for the archive only.
- The library holds four fictional demo cases (marked MOCK) in three functional areas.
- Design: one light appearance with a translucent toolbar and an Ask / Get asked segmented control, following Apple's Human Interface Guidelines (applied with the apple-design skill, github.com/dickwu/apple-design-skill). Get asked keeps a sidebar with the case and its interviews; Ask uses the full width.

To use the skill from any case folder, copy `.claude/skills/brian` to your personal skills folder (`~/.claude/skills/brian`).
